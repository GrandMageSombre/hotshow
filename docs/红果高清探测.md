# 红果短剧高清（480p/720p）探测记录

> 探测时间：2026-11-04
> 结论：**网页端拿不到 480p/720p 的明文，`lib` 侧不做改动。**
> 本文留档，避免以后重复踩坑。

## 一、网页播放器只有 360p

播放页 `/player/{series_id}/{vid}` 的 loaderData 里：

| 字段 | 值 |
| --- | --- |
| `protectedPlayback` | `true` |
| `publicVideoSeo` | `{width: 360, height: 640}` |
| `videoList` | `{}`（空） |

站点前端 JS（`detail.ccd29970b4.js`）里播放地址是写死的：

```js
o = function (t) { return i(t) ? "/video/public/".concat(t, "/360p.mp4") : "" }
```

没有清晰度分支，也没有清晰度菜单。

实测 `/video/public/{vid}/` 下 144p～4k、`origin`/`hd`/`sd`、`*.m3u8`
共 20 多种写法**全部 404**；`?quality=720`、`?definition=hd`、`?ratio=720`
等 query 一律被忽略（返回的还是同一份 1198345 字节）。

换移动端 UA、红果 App UA、加/不加 Referer、换 `hongguoduanju.com` 裸域，
结果都不变。

对照数据（同一集，时长 174.186s）：

| 档位 | 分辨率 | 码率 | 单集大小 | 能否直连 |
| --- | --- | --- | --- | --- |
| 360p | 360x640 | ≈ 55 kbps | 1.14 MB | ✅ 明文 |
| 480p | 480x854 | 1.06 Mbps | 16.5 MB | ❌ 加密 |
| 720p | 720x1280 | 1.59 Mbps | 26.9 MB | ❌ 加密 |

360p 的 55 kbps 是「秒开预览」级别的码率，所以画面糊得明显 —— 这不是播放器的问题。

## 二、480p/720p 确实存在，但走加密通道

匿名 `POST /api/video/protected/play-info`（`Content-Type: application/json`）
就能拿到 480p/720p，**不需要登录、不需要签名**：

```json
{"series_id": "…", "item_id": "…", "definition": "720p"}
```

返回 `play_info`：

| 字段 | 720p 实测值 |
| --- | --- |
| `width` / `height` | 720 / 1280 |
| `bitrate` | 1589990 |
| `size` | 26894791 |
| `format` | `dash`（video / audio 分离） |
| `init_range` / `index_range` / `first_moof_range` | `0-1276` / `1277-1728` / `1729-6006` |
| `kid` | `6ae08fa7476d5aacd8bebfd90002ebeb` |
| `player_access_key` | base64，解码后 **37 字节** |
| `expires_at` | 约 1 小时后失效 |

`1080p` 返回 `{"error":"protected_playback_unavailable"}`，最高就到 720p。

## 三、为什么解不开

下载 init 段（1277 字节）解析 box：

```
ftyp / moov(trak/mdia/minf/stbl → encv + sinf(schm=cenc, schi/tenc))
```

- `encv` 说明视频轨被当作加密轨；
- `tenc` 里 `default_isProtected = 1`、`default_Per_Sample_IV_Size = 16`、
  `default_KID` 与接口返回的 `kid` 一致；
- `moof` 里带 `senc`（125 个 sample，每个 16 字节 IV + `clear=110 / encrypted=35824`）；
- **没有 `pssh`** —— 不是 Widevine/PlayReady 那套标准 DRM，
  密钥由应用层自己传。

也就是说：拿到的是 CENC-AES-CTR 密文，**密钥不在网页里**。

验证过程：自己写了个 AES-128（FIPS-197 C.1 向量自检通过），
按 CTR 规则解第一个 sample 的 `[110, 110+35824)` 字节，试了 9 种候选 key
（`player_access_key` 的前/中/后 16 字节、`kid` 本身、`md5(ak)`、
`sha256(ak)[:16]`、`md5(kid)`、`sha256(kid)[:16]`），
解出来**没有一个能命中 H.264 的 `00 00 00 01` 起始码**。

`player_access_key` 本身是 37 字节且跟 URL 签名同步过期，更像「播放鉴权票据」，
不是内容密钥。真正的内容密钥只在红果 App 的 native 代码里。

顺带排除的路：

- `/api/video/protected/download-info`、`/play-info-token`、`/drm-key`、`/key`
  等 6 个猜出来的路径，全部 404；
- 给 `play-info` 加 `need_encrypt:false`、`drm:0`、`clear:true`、`no_drm:1`
  等 8 种参数，返回内容一字不差；
- 把 CDN 路径里的 `media-video-avc1` 换成 `media-video`、`media-video-mp4`、
  `media-video-clear` 等 8 种明文兄弟，全部 403（URL 签名绑定了路径）。

## 四、结论与取舍

1. **360p 是网页端对访客开放的上限**，这不是抓取没写好，是站点就这么设计的。
2. 480p/720p 技术上拿得到 URL，但要解开 CENC 才能用 —— 而密钥在官方 App 里，
   绕过它属于「规避技术措施」，有法律风险，**不做**。
3. 想要 720p/1080p，正路是用红果官方 App（App 内有清晰度切换）。
4. 本项目的红果页保持 360p，并在页面上明确标注，避免用户误以为是播放器没切清晰度。
